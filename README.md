# Dispatch

A lightweight job scheduler for **one** Linux workstation dedicated to scientific
simulations — primarily CFD.

Dispatch is not Slurm. It manages a single machine, has no users, no permissions, and no
network surface. It exists so that a headless workstation accessed over SSH feels like a
small HPC cluster: submit a case, walk away, and find a complete record of what ran.

```
  dispatch          Textual TUI + CLI, disposable
       │            AF_UNIX socket, newline-delimited JSON
  dispatchd         daemon: scheduler, executor, database
       │
  simulations       setsid'd process groups, outliving both
```

## Install

Needs Python 3.13 and Linux. On a fresh Debian 13 machine:

```sh
sudo apt install python3.13 python3.13-venv   # or: uv python install 3.13
git clone <repo> dispatch && cd dispatch

uv sync                      # create the environment from uv.lock
uv pip install -e .          # install `dispatch` and `dispatchd`

uv run dispatch doctor       # check this machine's setup
uv run dispatch              # start the interface (starts a daemon if none is running)
```

No systemd configuration is required. `dispatch` starts a daemon when it finds none, and
on Debian's default `logind` settings that daemon survives logout. `dispatch doctor` tells
you if your machine is configured otherwise, and what to do about it.

A systemd user unit and an annotated configuration file are in [packaging/](packaging/) if
you want the daemon started at boot.

## Use

```sh
dispatch                                  # the interactive interface
dispatch submit ~/cases/wing --cores 20   # queue a case
dispatch submit ~/cases/wing --cores 20 --dry-run   # show what would happen; run nothing
dispatch submit ~/cases/wake --cores 8 --after 3f2a  # start only once job 3f2a completes
dispatch status                           # machine and queue
dispatch ls                               # active jobs
dispatch logs <id> -f                     # follow a job's output
dispatch search 'tag:paper cores>=16 endTime>500'
```

In the interface: `1` dashboard, `2` queue, `3` history, `n` new job, `?` help. It is
entirely keyboard-driven.

## What it does

**Runs your case without you preparing it.** Ask for 20 cores on an OpenFOAM case
decomposed for 8 and Dispatch reconstructs, removes the old processor directories,
re-decomposes, and launches — after telling you that is what it is about to do. It does
*not* reconstruct afterwards: the decomposed case is left exactly as the solver left it.

**Never guesses.** No project-location heuristics: you browse to a case. Solver detection
reads `system/controlDict`, SU2 config keys, Basilisk includes, or CalculiX deck keywords,
and when detection is unambiguous it never asks which solver to use.

**Tells you before it acts.** `--dry-run` prints the exact commands, generated by the code
that would run them rather than by a description of it.

**Remembers everything.** Every run keeps its logs, its case metadata, its peak memory, and
a reproducibility record: the git commit of the case, whether the working tree was dirty,
the solver build, the exact `argv`, and a hash of the environment. Six months later you can
answer what produced a figure.

**Searches all of it.** `tag:paper solver:openfoam cores>=16 endTime>500 after:2026-01` —
free text mixed with typed terms, over years of history.

**Stays out of the way.** The daemon spends its life asleep: no polling, no tick loop, and
no measurement at all while nobody is watching the dashboard.

## Design

* **Nothing interrupts a simulation.** Not a dropped SSH session, not a TUI crash, not a
  daemon restart, not an upgrade. Jobs run in their own sessions; a restarted daemon
  re-adopts them and still recovers their exit codes.
* **The scheduler knows nothing about solvers.** Adapters return declarative execution
  plans; the daemon runs them. A test greps the daemon for `foam` and fails if it appears.
* **Admission is decided on a ledger, not measured load.** A solver blocked on I/O reads as
  idle, so measurement-based admission would oversubscribe exactly when the machine is
  already struggling. Dispatch and `htop` sometimes disagree, correctly.
* **Honest history.** A job whose machine was reset mid-run is recorded `UNKNOWN`, not
  `FAILED`. A gap is better than a confident wrong answer.

`docs/ARCHITECTURE.md` is the design of record: every module, the protocol, the adapter
interface, the schema, and a decision log giving the rationale *and the rejected
alternative* for each significant choice.

## Solvers

| Adapter | Detects | Parallelism |
|---|---|---|
| OpenFOAM | `system/controlDict` | `mpirun`, with automatic decomposition management |
| SU2 | `*.cfg` containing SU2 keys | `mpirun`; SU2 partitions internally |
| Basilisk | `*.c` including Basilisk headers | `qcc -D_MPI=N`, compiled as a preparation step |
| CalculiX | `*.inp` containing `*STEP` | `OMP_NUM_THREADS` |

Adding one means writing one adapter and nothing else. See
[docs/adapters.md](docs/adapters.md).

## Development

```sh
uv sync --all-extras
uv run pytest              # 483 tests, ~9s
uv run ruff check .
uv run mypy
```

The test suite runs without any solver installed: adapters are tested by asserting on the
command lists they produce, which is a direct consequence of plans being data.
